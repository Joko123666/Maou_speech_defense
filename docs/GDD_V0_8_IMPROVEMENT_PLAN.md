# 1. 종합 판단

v0.8의 핵심 문장인 “다섯 후보 중 한 명을 고르면 남은 네 후보 진영이 네 번의 공식 난입을 담당한다”는 기존 10분·4보스 구조에 세계관과 반복 동기를 동시에 부여한다. 현재 핵·목표지점·유니크 편대·도전 단계·결과 타임라인도 대부분 재사용할 수 있어 방향은 타당하다.

다만 문서의 구현 순서를 그대로 적용하면 다음 네 축이 동시에 변경된다.

1. 핵·목표지점의 표시 의미와 UI
2. 4종에서 5종으로 늘어나는 플레이어 콘텐츠
3. 고정 보스 배열에서 동적 경쟁 진영 계획으로 바뀌는 스테이지 구조
4. 후보 지지도·당선·칙령이 추가되는 영구 저장과 정산

따라서 개선 작업은 단순 리스킨이 아니라 다음 순서로 분리한다.

> 표시 계층 분리 → 선거 데이터 계약 → 기존 4종 수직 절편 → 런타임 보스 계획 → 5번째 후보·심복 → 고유 기믹 → 지지도·당선 → 최종 리소스

첫 목표는 모든 기능을 한 번에 넣는 것이 아니라, 기존 전투 수치를 유지한 한 후보·한 심복·한 고정 스테이지로 선거 콘셉트가 실제 플레이에서 읽히는지 확인하는 것이다.

# 3. 구현 전 확정할 설계 결정

## 3.1 후보와 전투 핵 데이터의 권위

`CoreData`에 후보 이름·칭호·진영·지지도·칙령 필드를 모두 추가하지 않는다. 후보는 선거 콘셉트의 메타/표시 정보이고 Core는 전투 규칙이므로 다음처럼 연결한다.

```text
CandidateProfileData.id
  ├─ core_id → CoreData
  ├─ faction_id → ElectionFactionData
  ├─ candidate_boss_id → EnemyData
  ├─ default_retainer_id → RetainerProfileData
  └─ decree_ids → CandidateDecreeData
```

기존 `CoreData.unique_tower_id`와 `unique_formation_id`를 전투상 권위로 유지한다. 후보 프로필에 같은 값을 중복 저장하지 않고 검증 시 연결된 Core에서 조회한다.

심복도 같은 원칙으로 `RetainerProfileData.cursor_id → CursorData` 연결을 사용한다. 이렇게 하면 다른 콘셉트 팩은 Core/Cursor만 사용하고 선거 전용 필드를 강제로 가질 필요가 없다.

## 3.2 안정 ID 정책

- 기존 전투 ID `emerald`, `iron` 등은 세이브·특화·유니크 참조 호환을 위해 유지한다.
- 후보 ID `partason`, `jiane`, `kasuha`, `irelai`, `judaginda`는 새 메타 진행의 안정 키로 사용한다.
- 심복 ID도 캐릭터 기준 안정 키를 별도로 둔다.
- 표시명 변경은 ID 변경 사유가 아니다.
- 결과·체크포인트·메트릭에는 표시명이 아니라 후보·심복 ID를 기록한다.

## 3.3 보스 카탈로그와 보스 일정 분리

현재 `ContentPackData`는 `stage.boss_times.size() == bosses.size()`와 카탈로그 마지막 보스가 최종 보스라는 계약을 가진다. v0.8에서는 이를 다음처럼 분리한다.

```text
보스 카탈로그
  = 출현 가능한 모든 후보·심복·간부

StageData.boss_times
  = 해당 스테이지의 네 난입 슬롯 시간

StageRuntimeBossPlan
  = 이번 런에 실제 출현할 4개 boss_id와 faction_id
  = 마지막 항목이 이번 런 final_boss_id
```

`StageData.final_boss_id`는 비선거 스테이지와 고정 계획의 폴백으로 유지한다. 선거 런에서는 런 시작 시 확정한 `StageRuntimeBossPlan.final_boss_id`를 승리 판정의 권위로 사용한다.

## 3.4 일반 적 행동과 진영 외형 분리

일반 적 18종을 진영마다 복제해 72개 이상으로 늘리지 않는다.

```text
EnemyData = 체력·속도·행동·보상
FactionPresentationData = 팔레트·문양·깃발·대사·짧은 패시브
SpawnRequest = enemy_id + faction_id
```

초기 수직 절편에서는 적 판정을 그대로 두고 팔레트·문양만 바꾼다. 진영 패시브는 가독성 검증 뒤 최대 1개씩 추가한다.

## 3.5 친위대 진형 레시피

v0.8 후보 설명의 일부 레시피는 전용 타워 2기·일반 타워 1기·공란 1칸이다. 이는 v0.7의 “전용 1기·일반 1기·공란 2칸” 및 시각적 혼잡 억제 계약과 충돌한다.

초기 구현은 v0.7 계약을 유지한다.

```text
친위대 1 / 공용 지원대 1 / 공란 2
```

전용 타워 2기가 콘셉트상 필수인 후보는 실제 10분 기여도와 화면 혼잡을 측정한 뒤 후보별 예외로 승인한다. 이때 기대 지수와 출현 확률도 함께 다시 계산한다.

## 3.6 주요 경쟁 후보 결정

주요 경쟁 후보를 임의 RNG로만 정하면 출격 화면 예고와 재현성이 깨진다. 다음 계약을 사용한다.

- 전투 RNG와 분리된 캠페인 계획 시드 사용
- 출격 확정 전에 4개 진영과 순서를 미리 생성
- 선택 후보는 반드시 제외
- 마지막 슬롯은 주요 경쟁 후보 본인
- 플레이어 심복과 중복되는 적 심복은 대체 간부로 교체
- 확정 계획 전체를 `GameSession`, 체크포인트, 결과에 저장
- 같은 시드·후보·심복·스테이지는 같은 계획 생성

초기 정책은 후보별 지정 라이벌 표를 권장한다. 완전 무작위나 가중 랜덤은 플레이 지표가 쌓인 뒤 추가한다.

## 3.7 지지도와 당선 수치

현재 GDD에는 비중과 실패 보상 비율은 있지만 기본 지지도, 후보별 당선 요구량, 보스별 지급량이 확정되지 않았다. 구현 전에 다음 목표를 먼저 고정한다.

- 도전 0 기준 첫 당선 목표 런 수
- 2:30 이전 반복 실패의 시간당 효율 상한
- 7:30 실패와 완주 보상의 비율
- 도전 10의 지지도 보너스 상한
- 당선 후 중복 당선 정산 규칙

권장 시작점은 한 후보당 8~12회의 정상적인 런으로 첫 당선이다. 실제 수치는 별도 계산 테스트에서 조정한다.

## 3.8 통치 지지율 범위

통치 지지율은 당선한 후보로 시작한 런부터 0~100 범위에서 변한다. 승리 시 기본 8에 도전 2단계마다 1을 더하되 도전 보너스는 최대 5로 제한한다. 패배 시 `ceil((1 - 진행률) × 10)`과 최소 손실 2 중 큰 값을 기본 손실로 사용하고, 격파한 경쟁 보스 수만큼 완화하되 최종 손실 1은 남긴다. 당선이 발생한 그 런은 50으로 초기화만 하고 통치 변동을 중복 적용하지 않는다. 시즌 감소, 일일 유지, 반복 노동과 전투 능력치 보너스는 도입하지 않는다.

| P3 | 지지도·당선·칙령 | 안정된 후보 ID/결과 | 대 | 세이브 v7과 장기 진행 |
| P4 | 최종 아트·사운드 | 규칙·UI 승인 | 매우 큼 | 출시 품질 리소스와 성능 검증 |

동적 보스 계획은 5번째 후보보다 코드 구현을 먼저 할 수 있지만 실제 기본 게임에서 활성화하는 시점은 후보 5종이 모두 준비된 뒤로 둔다. 그전에는 합성 테스트 팩으로 선택 1·경쟁 4 계약을 검증한다.

# 7. 자동 검증 계획

## 7.1 콘텐츠 계약

- 후보·심복 각 5종, ID·짧은 이름 중복 거부
- 후보→Core·진영·후보 보스·칙령 참조
- 심복→Cursor·기본 후보·대체 보스 참조
- Core의 친위대/진형 참조와 후보 프로필 일치
- 진영별 문양·팔레트·보스 풀 존재
- 선거 캠페인이 없는 기존 팩 정상 로드

## 7.2 보스 계획

- 선택 후보 제외 후 경쟁 진영 정확히 4개
- 결정적 시드 재현
- 마지막 슬롯=주요 경쟁 후보=최종 보스
- 플레이어 심복 중복 시 대체 보스
- 부족한 대체 보스는 시작 전에 검증 실패
- 전체 보스 카탈로그 수와 슬롯 수가 달라도 정상
- 결과 타임라인과 체크포인트가 같은 계획 사용

## 7.3 전투 기믹

- 환혹 재적용 면역과 보스 변환
- 넉백과 환혹의 독립 적용
- 사령 충전 상한과 풀 회수
- 친위대 소모·행동불능·재가동
- 선고 3중첩, 일반 처형, 보스 고정 피해
- 합동 공격 뒤 주그디에드의 이동·회수 유지
- 돌격부대 최소 1인과 충원 시간
- 1×·2×·3× 게임 시간 등가성

## 7.4 저장·정산

- v6→v7 마이그레이션
- 신규 필드 타입·범위 검증
- 후보별 지지도 분리
- 동일 `run_id` 중복 방지
- 체크포인트 복구 후 같은 후보에 정산
- 당선 1회 처리와 칙령 보존
- 주 파일·백업·회전 슬롯 복구 회귀

## 7.5 UI

- 후보 5카드와 심복 5카드의 키보드·패드·터치 탐색
- 1280×720, 긴 이름, 긴 구호, 잠금/당선 배지
- 다음 난입 진영 4개와 주요 경쟁 후보 예고
- 심복 자원·행동불능·친위대 재가동 표시
- 결과 지지도 카운트업과 당선 이벤트
- 기존 Formation Defense 프로필의 UI 회귀

# 9. 주요 위험과 대응

## 보스 계획이 공유 Resource를 변경하는 문제

공유 `StageData`나 `EnemyData`를 런 중 수정하지 않는다. 모든 선택 결과는 런타임 값 객체에 저장하고 스포너·결과·체크포인트에 주입한다.

## 표시명과 안정 ID 혼용

세이브·메트릭·참조에는 ID만 사용하고 표시명은 화면 생성 시 프로필에서 조회한다. 후보 개명으로 진행도가 초기화되지 않아야 한다.

## 선거 전용 필드가 범용 전투 데이터를 오염시키는 문제

Candidate/Retainer/Faction Resource를 Core/Cursor/Enemy와 분리한다. 연결 ID와 교차 검증만 ContentPack 경계에서 수행한다.

## 신규 기믹이 GameController를 더 키우는 문제

환혹, 사령, 재가동, 선고, 합동 공격을 각각 상태/전략/서비스로 캡슐화한다. `GameController`는 이벤트 연결과 런 흐름만 담당한다.

## 리스킨 문자열 누락

씬의 기본 텍스트는 에디터 미리보기용 폴백으로만 두고 런타임 필수 문구는 `GameTextCatalogData`가 검증한다. 개발 빌드에서 누락 키 목록을 출력한다.

## 최종 아트 선투자

1조합 수직 절편과 4종 회색 상자 테스트가 승인되기 전에는 후보 전체 일러스트·보이스를 일괄 제작하지 않는다.

# 10. GDD v0.8에 반영을 권장하는 정정

1. 친위대 진형 예시를 기본적으로 “친위대 1·공용 1·공란 2”로 맞추거나, 2기 배치를 의도한 예외라고 명시한다.
2. `CandidateProfileData`와 `RetainerProfileData`를 Core/Cursor에 직접 필드를 추가하는 안보다 우선안으로 명시한다.
3. `CampaignBossPlan`은 정적 Resource가 아니라 런마다 생성되는 직렬화 가능한 계획이라는 점을 명시한다.
4. 전체 보스 카탈로그와 스테이지의 네 보스 슬롯을 분리한다.
5. 주요 경쟁 후보의 결정 규칙과 계획 시드·미리보기·체크포인트 보존 규칙을 확정한다.
6. 후보 지지도 기본값·당선 요구량·첫 당선 목표 런 수를 구현 전에 수치화한다.
7. 통치 지지율은 당선 다음 런부터 승패·도전 단계·진행도·격파 보스로 증감하고 외형·대사 반응만 바꾸며 전투 능력치에는 연결하지 않는다.
8. 진영별 일반 적은 행동 데이터 복제보다 `EnemyData + FactionPresentationData` 조합을 우선한다.
9. 세이브 계약을 v7로 올리고 v6 마이그레이션·중복 정산 테스트를 완료 기준에 추가한다.
10. 선거 문구 전체 교체를 위해 `GameTextCatalogData` 또는 동등한 키 기반 텍스트 계약을 추가한다.

# 11. 최종 완료 정의

v0.8은 다음 조건을 모두 만족할 때 완료로 본다.

1. 후보 5종과 심복 5종을 자유 조합할 수 있다.
2. 선택 후보를 제외한 네 진영의 보스 계획이 출격 전에 결정되고 결과까지 유지된다.
3. 최종 슬롯의 주요 경쟁 후보를 제압해야만 연설 완주가 된다.
4. 기존 10분 전투, 편대, 특화, 리롤, 도전 단계, 자금, 업적, 도감, 체크포인트가 회귀하지 않는다.
5. 신규 기믹은 상한·저항·상태 머신·3× 배속 검증을 가진다.
6. 후보 지지도와 당선은 같은 런을 두 번 정산하지 않으며 v6 저장을 안전하게 이전한다.
7. 후보·심복·진영·지원대가 색상 외 문양과 실루엣으로 구분된다.
8. 기본 Formation Defense 프로필과 마계 총선거 프로필이 같은 코드에서 각각 유효하게 실행된다.
9. 대형 오케스트레이터와 단일 스모크 러너에 신규 시스템 로직을 직접 누적하지 않는다.

가장 먼저 실행할 실제 작업은 단계 0과 단계 1이다. 특히 보스 카탈로그와 런타임 보스 계획의 분리 계약을 테스트로 먼저 고정해야 이후 5번째 후보, 경쟁 진영, 결과·지지도 시스템을 재작업 없이 연결할 수 있다.
