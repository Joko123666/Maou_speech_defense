## 1. 종합 판단

v0.10은 단순 수치 조정이 아니라 후보 성장의 권위를 일반 레벨업에서 보스 처치 이벤트로 옮기고, 친위대를 시작 보너스에서 독립 성장축으로 승격하는 구조 개편이다.

현재 구현에는 다음 기반이 이미 있다.

- 2:30·5:00·7:30·10:00 보스 슬롯과 런별 경쟁 후보 계획
- 후보 5종과 Core, 심복 5종과 Cursor의 안정 ID 연결
- 전투 시작 전 `PREPARATION` 친위대 배치와 4×6 보드
- 일반 레벨업 3택, 하위 특화 3택, 순차 등장과 입력 잠금
- 환혹, 선고/처형, 사령 충전, 부활 친위대, 보스 제어 내성
- 1×·3× 전투 감사, 효과 밀도 예산, 메트릭과 UI 스냅샷

v0.10의 핵심 성장 흐름은 현재 실행 코드에 연결됐다.

- 친위대 훈련→특화→완성의 런 내 성장 상태와 후보별 15개 행동을 구현했다.
- 공격속도와 받는 피해 증가를 공통 계산 경계에서 합산·상한 처리한다.
- 카스하 심연체, 이레라이 사령·죽음의 파도, 심연의 기둥 제물이 공통 `SummonService`의 즉시 예약·반환 계약을 사용한다.
- 결과·체크포인트·감사 스키마에 후보/친위대 성장과 소환 피크·예산 비용을 연결했다.

GDD v0.10 기능 구현과 구조 개선을 동결한 뒤 2026-08-20 최신 코드로 Godot 파싱, 18개 계약·게임플레이 스모크, Forward Mobile UI 55화면, 5후보×3시드 장기 품질·성능 게이트를 한 묶음으로 완료했다. 따라서 세 집중 항목의 남은 기능 추가나 검증 부채는 없으며, 이후 작업은 별도 밸런스·경제·표현 폴리시와 보류 중인 모바일·배포 준비다.

따라서 구현 순서는 다음으로 고정한다.

```text
데이터 계약
→ 보스 보상 큐와 후보 성장 분리
→ 친위대 희소 템플릿
→ 공통 전투 규칙
→ 후보 5종 수직 절편
→ 친위대 3단 성장
→ UI·결과·메트릭
→ 5후보×다중 시드 최종 검증
```

## 3. 구현 전 확정할 설계 결정

### 3.1 성장 트리거는 시각이 아니라 보스 슬롯 제압

권장안:

- `boss_plan.slots`의 0·1·2번 보스를 실제로 처치했을 때만 후보 성장을 지급한다.
- 150·300·450초가 지나도 해당 보스가 살아 있으면 강화는 지급하지 않는다.
- 동일 보스 ID 중복 신호와 체크포인트 재정산을 막기 위해 슬롯별 지급 플래그를 둔다.
- 3번 최종 보스는 성장 없이 결과로 전환한다.

이 방식은 GDD의 표기 시간과 “보스 처치 후” 조건을 동시에 만족한다.

### 3.2 중첩 모달은 보상 큐로 직렬화

보스 처치 순간 일반 레벨업·편대 배치·다른 후보 보상이 열려 있을 수 있다.

권장 우선순위:

```text
현재 열린 편대 배치 완료/포기
→ 후보 보스 이정표 보상
→ 누적된 일반 레벨업 보상
```

`ProgressionRewardQueue`가 보상 종류와 원인 보스 슬롯을 보존하고 한 번에 하나의 패널만 연다. 후보 5분 특화는 리롤·뒤로가기·포기 없이 반드시 한 장을 선택한다.

### 3.3 후보와 Core의 상태 분리

`CoreData`는 기본 공격·액티브·체력 등 전투 원형을 유지한다. 선거 전용 성장은 별도 데이터가 소유한다.

```text
CandidateProfileData
  └─ growth_profile → CandidateGrowthData
       ├─ first_fixed_upgrade
       ├─ branches[3]
       └─ final_fixed_upgrade

CandidateGrowthState
  ├─ completed_boss_slots
  ├─ selected_branch_id
  └─ accumulated_resources
```

기존 `core_state`는 외부 콘텐츠 팩 호환 어댑터로 한 단계 유지하되 선거 프로필에서는 일반 레벨업과 수치 계산에 사용하지 않는다. 장기적으로 `LoadoutManager`에서 후보 상태와 Cursor 성장 상태를 완전히 분리한다.

### 3.4 친위대는 심복과 다른 용어·데이터 축

- 심복: 선택한 `RetainerProfileData`와 Cursor 전투 개체
- 친위대: 선택 후보의 시작 `TowerFormationData`와 그 안의 병력

`GuardGrowthData`는 후보 ID 또는 친위대 편대 ID에 연결한다. 심복 특화와 섞지 않는다.

### 3.5 희소 친위대 템플릿 표현

현재 `FormationCellData`는 실제 점유 셀만 저장하므로 GDD의 `0` 셀은 별도 예약 데이터가 필요 없다. 떨어진 셀의 오프셋만 보존하면 그 사이를 일반 편대가 사용할 수 있다.

일반 편대 검증은 현행을 유지한다.

- 2~4셀
- 직교 연결

친위대만 예외를 허용한다.

- 2~6셀
- 비연결 허용
- 좌표 정규화·중복·보드 범위 검증은 유지
- 템플릿 내부 `0` 위치의 일반 편대 배치 가능성을 계약으로 검사

### 3.6 친위대 병력 ID 정책

현재 후보당 전용 병력 ID는 한 개뿐이다. 주다긴다의 근접/원거리 혼성처럼 서로 다른 공격 규칙은 하나의 ID로 정확히 표현할 수 없다.

권장안:

- 기존 안정 ID는 대표 친위대 병력으로 유지한다.
- 실제 행동이 다른 경우에만 후보 전용 하위 ID를 추가한다.
- 최소 신규 후보는 주다긴다 근접/원거리 2종이다.
- 동일 행동의 반복 셀은 같은 ID를 여러 번 사용한다.
- 새 하위 ID는 전신 이미지 복제가 아니라 작은 역할 표식·무기 실루엣 변형으로 구분할 수 있으나, 에셋 별칭 정책은 별도 승인한다.

확정 필요:

- `obsidian_verdict`를 근접 또는 원거리 중 어느 쪽에 유지할지
- 카스하 전방 기둥에 일반 `slow`를 사용할지 친위대 전용 기둥 ID를 만들지

### 3.7 수치가 미정인 표현의 초기값

“소폭·대폭·일정 주기”는 데이터에 이름 있는 상수로 먼저 넣고 감사로 조정한다. 코드에 임시 숫자를 흩뿌리지 않는다.

초기 상한 권장안:

| 항목 | 초기 상한 |
|---|---:|
| 공격속도 최종 배율 | ×1.75 소프트캡 |
| 런 내 영구 공격속도 | 추가 +30% 하드캡 |
| 일반 적 받는 피해 증가 | +100% |
| 보스 받는 피해 증가 | +60% |
| 후보 영구 공격력 스택 | GDD 예시 40스택 |
| 헌신 | 30스택·최대 +3초 |
| 순교 | 30스택·최대 +15% 공속 |
| 영혼수확 | 300, 100 단위 체감효율 |
| 죽음의 저주 | 3세대 |

최종 수치는 대표 5후보×3시드 600초 감사 전에는 확정값으로 기록하지 않는다.

### 3.8 문서 내 모호점

구현 전에 다음을 결정한다.

1. 카스하 `후보 레벨 비례`는 일반 레벨이 제거되므로 후보 성장 단계 0~3 비례로 해석할지 플레이어 레벨 비례로 할지. 권장: 후보 성장 단계.
2. 파르태손의 `왕권 선포`는 권장 예시인지 기존 에메랄드 액티브를 대체하는 필수안인지. 친위대 C가 이에 의존하므로 필수 교체를 권장한다.
3. 친위대 훈련 카드가 런마다 반드시 완성 가능한지. 권장: 적격 상태에서 2회 연속 미제시 후 보장하되 화면당 최대 1장.
4. 주다긴다의 현재 전체 이름 `주다긴다 벨 세라프`를 GDD 표기 `죽음교주 주다긴다`로 바꿀지. 안정 ID는 무조건 유지한다.

| 서비스 | 책임 |
|---|---|

## 9. 다음 구현 묶음 권장 범위

### 묶음 A — 구조 개선 종료선 확정 (P0, 완료, 비모바일 +1.2%p)

1. `_present_tower_hit()`을 연출 프로필 산출, 효과 예산·생성, 피격 피드백으로 분리한다.
2. 이레라이의 재가동→첫 타격→사망→다음 사령 저주 전파를 한 장면에서 확인하는 통합 계약을 추가한다.
3. 이후에는 행 수가 아니라 책임 혼합, 중복 규칙, 회귀 위험이 확인된 코드만 분리한다. 신규 결함이 없으면 구조 개선을 종료하고 코드 동결로 전환한다.

완료 조건: 전투 수치·판정·이벤트 순서 변경 없음, 관련 계약 추가, 변경 목록 동결.

완료 결과(2026-08-20): 피해 대비 강도·행동별 반경을 순수 `TowerHitPresentationProfile`로 이동하고 `_present_tower_hit()`을 9행 조정기, 7행 효과 생성기, 4행 적 피드백 함수로 분리했다. 이레라이 재가동 컴포넌트 신호→첫 공격 저주 I→사망→사령 II·III→계보 종료의 장면 통합 계약을 작성했으며 최종 일괄 스모크에서 통과했다.

### 묶음 A2 — 레거시 배치 경로·성장 책임 정리 (P0, 비모바일 +4.0%p)

1. 실제 런에서 도달하지 않는 `LevelUpPanel.show_placement()` 6열 UI와 `UpgradeSelectionRouter.COLUMN_PLACEMENT`의 저장·외부 팩·테스트 의존성을 확인한 뒤 제거 또는 명시적 호환 모듈로 격리한다.
2. `TowerFormationData`를 현재 블록 셀 데이터로 단일화하고, 명시적으로 격리된 구형 열 테스트 픽스처와 `LegacyColumnFixtureCatalog`·`LegacyColumnSnapshotAdapter`를 최종 제거한다.
3. `LoadoutManager.apply_upgrade()`의 성장 적용은 전용 서비스로 분리하고, 편대 배치 44행과 강화 후보 생성 42행을 보드 배치 서비스·제안 생성기로 분리한다.
4. 제거 대상 UI·라우트·필드가 코드·씬·스냅샷·계약에서 함께 사라지는지 정적 감사한다.

완료 조건: 실제/테스트 런이 같은 블록 보드 경로를 사용하고, 저장 호환 경계를 제외한 레거시 열 UI·라우트·4행 전투 레시피가 남지 않으며 성장 적용과 배치 실패 복구 순서가 보존됨.

완료(2026-08-20): `LevelUpPanel`의 6열 설치 패널과 열 미리보기·반전·단축키 코드, `UpgradeSelectionRouter.COLUMN_PLACEMENT`, `LoadoutManager.get_valid_placement_columns()`을 제거하고 일반 편대 배치는 4×6 `PreparationPanel`만 사용하게 했다. 병력·핵·목표지점·친위대·전역·상태 성장 적용은 `LoadoutUpgradeApplicationService`로 이동해 GDD 상한·분기·신호 규칙을 독립 계약으로 고정했다. `TowerFormationData.tower_ids`와 구형 생성·공란 API를 제거해 `cells` 단일 스키마로 통일했고, UI 스냅샷 6곳과 대형 스모크의 마지막 열 전투도 실제 친위대 준비·블록 편대 배치·배치 소유권 조회로 이관했다. 그 결과 `LegacyColumnFixtureCatalog`, `LegacyColumnSnapshotAdapter`, 테스트 토글, 열 추천 필드와 `unique_formation` 레벨업 경로를 삭제했으며, 정적 계약이 해당 경로의 재도입을 차단한다. 편대 배치의 보드 커밋·열별 전투 슬라이스 생성·실패 롤백·소유권 제거는 `FormationPlacementService`로, 카드 3장 조합·편대 크기 가중치·후보 추출·두 천장 주입·리롤 복원은 `UpgradeOfferService`로 이동했다. 매니저의 배치와 제안 공개 진입점은 각각 14행과 3행으로 축소됐으며 묶음 A2의 구조 항목은 완료됐다.
